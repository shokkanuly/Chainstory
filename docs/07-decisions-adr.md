# 07 — Decision Log (ADR)

Format: **Context → Decision → Consequences → Revisit when.** Add new entries at the bottom; never rewrite history, supersede instead.

### ADR-001 — One product, not two
**Context:** Two planned efforts (EVM narrative/tax engine; Solana ZK Compression build).
**Decision:** Ship as ChainStory v2. Compressed-state explanation is a feature of the narrative engine.
**Consequences:** Shared UX, shared tax/reputation; Solana code must not leak into EVM modules.
**Revisit when:** Solana-specific needs (e.g. server indexing) contradict I2.

### ADR-002 — Stay a Vite React SPA (no Next.js)
**Context:** Source notes suggested Next.js App Router for the ZK build.
**Decision:** Keep React 19 + Vite. No SSR needed for a client-only tool.
**Consequences:** No framework migration cost; Photon calls are browser-side with user keys.
**Revisit when:** SEO/share-card rendering or server components become a real requirement.

### ADR-003 — Modules with enforced boundaries, not a monorepo (yet)
**Context:** Need isolation between chains and between domain and I/O.
**Decision:** Single package; folder layers; **boundary linter** (`eslint-plugin-boundaries` or `dependency-cruiser` — new dev-dependency, needs owner approval).
**Consequences:** Lower tooling cost; discipline enforced by CI rather than by package walls.
**Revisit when:** Build times or team size demand independent versioning, or a second app (e.g. attest UI) needs to share code.

### ADR-004 — Chain-agnostic `NormalizedTx` as the only seam
**Context:** Tax, classify, risk, pricing must not know about chains.
**Decision:** Adapters output `NormalizedTx` (`03`). CAIP-2 chain IDs; asset keys chain-qualified; compressed and standard tokens share an asset key.
**Consequences:** Some chain nuance becomes tags/roles; the model needs care when extended (change = update docs + all consumers).
**Revisit when:** A chain cannot be expressed without leaking (e.g. UTXO chains).

### ADR-005 — Balance-diff first for Solana
**Context:** Solana has no transfer logs; program decoding is unbounded work.
**Decision:** Amounts come from pre/post balances (and Photon compression info); program registry/decoders add meaning, never amounts.
**Consequences:** Correct amounts even for unknown programs; less protocol-specific detail until decoders exist.
**Revisit when:** A common protocol's semantics can't be inferred from diffs (e.g. some liquidity ops).

### ADR-006 — Provider abstraction and user-supplied keys
**Context:** No backend (I2); Photon needs a capable provider and usually a key.
**Decision:** `SolanaRpc` and `PhotonClient` take endpoints from Settings; degrade gracefully without Photon; no shared proxy.
**Consequences:** Users must bring keys; onboarding UX matters. No central rate control.
**Revisit when:** Adoption is blocked by key friction → consider an ADR-backed proxy (would be a deliberate I2 exception).

### ADR-007 — LLM off the critical path
**Context:** LLM prose is nice but nondeterministic and injectable.
**Decision:** Rules/ML classify; LLM only phrases from structured slots; never used in tax or risk verdicts; opt-in with data preview.
**Consequences:** Stories are reproducible offline; LLM stories are additive polish.
**Revisit when:** A validated on-device model can replace the cloud LLM.

### ADR-008 — `story-attest` is experimental and physically separated
**Context:** Writing to chain requires signing (conflicts with I1) and adds security surface.
**Decision:** Live in `programs/` + `scripts/attest/`, not the analysis bundle; gated by Phase 5 criteria and kill criteria.
**Consequences:** The read path never depends on it; effort only spent if a consumer exists.
**Revisit when:** A concrete consumer appears, or at the end of Phase 4 (drop if none).

### ADR-009 — Drop Firedancer/multi-client tooling; reframe "agent"
**Context:** Source notes listed Firedancer tooling and an AI agent that "blocks" drainers.
**Decision:** Firedancer is out of scope. The "agent" becomes **Guard**: read-only simulation + explanation + warnings (Phase 4).
**Consequences:** Scope stays coherent with a wallet-narrative product; no false promise of blocking.
**Revisit when:** A real integration point with signers exists (wallet extension) — separate product decision.

### ADR-010 — Compressed NFTs (Bubblegum) excluded from ZK Compression work
**Context:** Two different "compression" systems exist on Solana.
**Decision:** ZK Compression (Light) only, for now. cNFT support (DAS API) is a separate later item.
**Consequences:** Avoids conflating mechanisms in code and UI copy.
**Revisit when:** User demand for NFT history on Solana.

### ADR-011 — Numbers from code, words from models
**Context:** Hallucinated amounts in a financial tool are unacceptable.
**Decision:** Story headlines are templates with structured slots; LLM narrative is discarded if it introduces numbers/entities not in slots.
**Consequences:** Slightly less fluent prose; verifiable output.
**Revisit when:** Never for tax; possibly for purely decorative text.

### ADR-012 — Tripwire's write path is an operator component, outside the analysis app
**Context:** Tripwire must sign attestations and change on-chain state (pause, throttle, delay a bridge route). I1 makes the analysis app read-only; I2 forbids a ChainStory backend.
**Decision:** The write path — watcher, single-signer attestor, deploy scripts — lives in `scripts/tripwire/` and `contracts/`, run by a bridge operator. The analysis app never imports it, holds a key, or sends a transaction, so I1 and I2 still hold for the app. The attestation key is a throwaway testnet key in a git-ignored `.env`.
**Consequences:** One product, two runtimes: the browser app (read-only) and an operator process (writes). Single signer is a named centralisation point; 2-of-3 threshold signing is the production path.
**Revisit when:** Any code in `src/app` or the browser bundle needs a key, or the attestor moves to hosted infrastructure.
**Approved:** by the human, 2026-09-28.

### ADR-013 — A narrow, stateless key proxy for the EVM explorer and Gemini (an exception to I2 and I10)
**Status:** Approved by the human, 2026-09-28. Records code already in `api/` and `server/`. Supersedes ADR-006's "no shared proxy" for the EVM explorer and Gemini.
**Context:** Vite inlines every `VITE_*` variable into the client bundle, so the earlier build shipped the explorer and Gemini keys to every visitor. Moving them server side was a security fix, and it created `api/` + `server/` (Vercel functions). That contradicts I2 ("No ChainStory backend") and I10 ("API keys are user-supplied, stored locally"), and nothing recorded the exception. ADR-006 anticipated it: "consider an ADR-backed proxy (would be a deliberate I2 exception)".
**Decision:** Allow exactly two stateless functions, and nothing else server side:
- `/api/explorer` (`server/explorerHandler.ts`): Etherscan V2 only; an allowlist of module/action pairs, each parameter validated; ENS resolution built server side rather than a general `eth_call`.
- `/api/describe` (`server/geminiHandler.ts`): the prompt is assembled server side from structured fields, never sent by the client. The `/check` wording (`server/checkPhrasing.ts`) accepts only a badge and reason ids from a closed set.

Keys are server environment variables (`ETHERSCAN_API_KEY`, `GEMINI_API_KEY`), never `VITE_*`. No database, no accounts, no stored requests; a per-IP, in-memory rate limit. The same handlers run in the Vite dev server (`server/devPlugin.ts`) and in-process for Node (`server/explorerTransport.ts`, for the Tripwire watcher), so there is one code path. Solana / Photon keys stay user-supplied (ADR-006).
**Consequences:**
- "No backend" becomes "no backend that stores anything": two stateless proxies we pay for and must keep within quota. The in-memory limiter resets per instance and is not shared, so it stops casual scraping, not a determined attacker.
- Every explorer lookup now passes through our origin, so the host sees the requesting IP and the address looked up, and host request logs can record both. The privacy copy in `docs/06` §2 ("ChainStory has no server") is no longer true and must change with this ADR.
- With no key configured each path degrades rather than fails: explorer → 503 → labelled demo data or "unchecked"; describe → 503 → deterministic text.
- Found while writing this, not changed: `services/descriptionGenerator.ts` sends full `from`/`to` addresses and values to `/api/describe` for every classified transaction, automatically. `docs/06` §2 promises the LLM feature is opt-in, off by default, with a preview, and sends truncated addresses only. The `/check` wording sends no user data (fixed phrases only), so it is not affected. **Resolved 2026-09-29, by the human's decision:** AI descriptions are now opt-in, off by default, with a preview, and send shortened addresses only (`services/aiDescriptions.ts`); `docs/06` §2 describes the new behaviour.
**Reworded on approval (2026-09-28):** AGENTS.md §1 "Shape", I2 and I10; `docs/01` principle 1; `docs/02` "Browser-only means keys are user-supplied"; `docs/06` §2 privacy copy and §3 keys; and ADR-006 is superseded here rather than edited, per this log's rule.
**Revisit when:** a user-supplied-key mode is wanted again (restore Settings keys, keep the proxy as the fallback), or the proxy needs state (a cache, accounts, stored results) — that would be a real backend and needs its own ADR.

### ADR-014 — Tripwire release reviews are mandatory before demo payouts
**Status:** Authorized by the human's instruction to start the Tripwire hardening plan, 2026-09-30.
**Context:** The scripted demo waited for scoring and route protection, but ProtectedVault itself allowed anybody to execute a requested release first. Missing source data was also scored as a verified absence.
**Decision:** Add an oracle-signed, short-lived per-release review to the demo vault. Sign every payout field, its minimum guardian tier, and a monotonically increasing per-message nonce in a vault/chain-bound EIP-712 domain. PENDING and HELD requests cannot execute; REJECT is terminal. Fresh ALLOW still requires guardian protection and SafeERC20 transfer. All real signing stays in the operator scripts (ADR-012); no browser app signing, new dependencies, backend or persistent storage is added.
**Trust boundary:** The release reviewer can permit already requested payouts, a broader role than the guardian's tighten-only attestation. This review does not authenticate the bridge message or independently verify source-chain consensus. Production bridges must retain independent message/source verification. The demo source remains explicitly synthetic. Oracle rotation invalidates old execution allowances.
**Failure policy:** An unconfigured, unavailable or malformed source verifier means hold/retry. Only explicit independently established invalid backing may produce a terminal source rejection. Conflicting observed logs require reconciliation. Backing arithmetic is bigint; illustrative USD behavioral heuristics and incident reconstruction retain their earlier approximate representation.
**Consequences:** The gated vault must be freshly deployed; the recorded Sepolia vault is unchanged. Local tests and demo run actual vault bytecode. The operator must confirm required risk protection and review receipts before execution, then maintain durable retry state in the next milestone. The browser guardian replay is unchanged and does not demonstrate this vault gate.
**Revisit when:** selecting the first real bridge adapter, implementing durable operator state, replacing the single reviewer or changing the review/delay recovery policy. See [hardening plan](plans/tripwire-hardening.md).

### ADR-015 — Durable Tripwire operator state and signed transaction outbox
**Status:** Authorized by the human's instruction to continue the Tripwire hardening plan, 2026-09-30.
**Context:** In-memory watcher cursors could advance before a request was durably queued; a process restart lost pending/held/delayed work. Broadcasting before recording a transaction left its outcome ambiguous after a crash.
**Decision:** Add an operator-only SQLite store under `scripts/tripwire/`, using the existing Node runtime's `node:sqlite` (Node ≥22.13; no npm dependency). Store both feed cursors, validated events, pending/completed requests, conflicts and exact release history in one atomic snapshot. Amounts remain bigint at runtime and canonical decimal strings in storage. Use WAL with `synchronous=FULL`. Bind schema version and deployment scope (route, both chain IDs, source/vault/guardian/token, decimals and transaction sender); reject incompatible or malformed state rather than reset it.
**Ownership:** One operator per state file. A separate SQLite database holds an EXCLUSIVE transaction for the process lifetime, so competing operators fail and process death releases the lock automatically. This assumes one stable state-file path on a local filesystem; do not rename/delete the database or its `.lease` file while running. Browser analysis and stateless proxies have no database, keys or access to operator state (I1/I2 remain unchanged for those runtimes).
**Submission policy:** Prepare/sign locally, validate the signed transaction's chain/sender/payload/hash and durably record its original bytes before broadcasting. Recovery checks the original hash for a receipt, otherwise rebroadcasts identical bytes; no fresh nonce/transaction is allocated while a signed job is outstanding. Actual receipts resolve confirmed/reverted states. RPC errors/timeouts remain outstanding; a revert is recorded, never treated as success. The durable release runner acknowledges only matching on-chain EXECUTED/REJECTED states. HOLD and guardian-delayed releases remain pending and are reassessed, with fresh short-lived reviews for retries.
**Consequences:** This is persistent bridge-operator state, not a hosted ChainStory backend. Signed transactions are sensitive authorization material: local files are mode 0600 and ignored by Git. Snapshot storage is suitable for a single-route pilot; compaction/indexed state, gas replacement, competing external senders and multi-process operation remain future work. Receipt recovery does not establish canonical-chain finality: block-hash reconciliation/reorg handling is still a separate P0 milestone. Pending ALLOW bytes retain their signed TTL during recovery; they cannot bypass the vault's review expiry, signer binding or guardian checks.
**Validation:** Failure injection before/after writes and broadcasts, wrong scope/corrupt schema, exact large amounts, HOLD/delay recovery, repeated-operation deduplication, receipt persistence failure, and real SIGKILL before/after a SQLite commit. The existing public deployment is unchanged. The standalone Sepolia runner has no invented source proof/baseline and therefore holds unchecked requests; see [operator runbook](plans/tripwire-operator.md).
**Revisit when:** selecting a real bridge adapter, adding finality/reorg handling, scaling beyond one operator, rotating the transaction sender, or hosting operator infrastructure.

### ADR-016 — Finalized RPC observations, staged receipts and durable quarantine
**Status:** Authorized by the human's instruction to continue Tripwire hardening, 2026-09-30. Supersedes ADR-015's receipt-only completion policy for real-chain operator ports.
**Context:** A latest-chain log or first receipt may disappear in a reorg. Waiting for every review receipt to become finalized would consume the vault's short review TTL before execution. Recovering signed ALLOW/payout work before checking source anchors could also publish an authorization after the source history changed.
**Decision:** The standalone Ethereum/Sepolia operator ingests only the RPC's `finalized` range. Validate hash-linked headers (64-block chunks), log identity/contract/range and block/transaction provenance. Persist chain/contract/event/start-bound checkpoints with the observations. Revalidate committed anchors before recovery, signing, broadcasting and terminal acknowledgement. The explicit `local` mode is for fixture ports; `finalized` ports require canonical finality, publication-safety and conflict handlers, and bind that policy in the database scope.
**Receipt stages:** Persist signed → included → finalized confirmed/reverted. Canonical inclusion is sufficient to continue guardian/review/execution within the signed TTL; EXECUTED/REJECTED is acknowledged only from matching state at a hash-checked finalized block. Included reverts remain nonterminal until finalized. Ordinary unfinalized receipt reorgs reopen the original signed transaction, retain the orphaned receipt anchor and rebroadcast identical bytes. Missing receipts on a still-canonical block are RPC unavailability, not proof of a reorg. A finalized revert permits an explicitly numbered fresh review attempt; unresolved/confirmed attempts are not silently overwritten.
**Finality conflict:** Changed committed finalized source/destination or transaction block hashes persist a quarantine, discard cached backing/behavioral history and retain the queue/checkpoints/transaction bytes for investigation. Automatic verification, signing, publication and acknowledgements stop, including on restart. A finalized-history conflict is not auto-rewound or auto-resumed: consensus/provider reconciliation must precede an explicit migration and rescan. Existing broadcast signatures and on-chain allowances remain governed by their TTL and guardian; off-chain quarantine cannot instantly undo them or an already executed payout.
**Storage compatibility:** Schema v2 adds origin/checkpoint, included receipt/audit, finality-mode and quarantine contracts. V1 is refused without mutation/reset of its queue. Existing active operators must stop and reconcile/back up old signed work before an explicit migration; changing filenames to skip the error can hide outstanding nonces. No live operator/database migration or public deployment was performed here.
**Trust boundary:** This validates the provider's internally consistent canonical/finalized answers. It is not an Ethereum consensus light client, independent source proof, bridge-message authentication or a guarantee against a dishonest RPC. Real bridge and rollup finality require their own adapter policy; never substitute a generic block count or fall back to latest when finalized is unsupported. The scripted fast demo still uses instant synthetic observations explicitly.
**Validation:** Finalized-only ingestion/provenance, hash-linked headers, stale/unsupported RPC, restart anchor conflicts, staged receipt finality, orphaned raw-byte recovery, missing canonical receipts, late publication checks, durable quarantine, final terminal-state acknowledgement, legacy schema refusal and finalized review-revert retries. See the [operator runbook](plans/tripwire-operator.md).

### ADR-017 — CCTP v2 Standard USDC post-mint escrow source adapter
**Status:** Authorized by the human's instruction to continue Tripwire hardening; implemented 2026-10-01. Extends ADR-016 with a bridge-specific testnet policy, without enabling a live deployment.
**Context:** A same-chain MockSourceBridge event is not a burn proof. An authentic burn alone also does not prove the payout vault received funds. CCTP v2 emits a zero nonce, then assigns a nonce offchain; pairing releases by that emitted field would collide. Finalized transfers may carry fees, so gross burn amounts cannot authorize a larger net payout.
**Decision:** Start with Circle Standard USDC, Base Sepolia → Ethereum Sepolia. Require finalized canonical successful source and destination receipts, source MessageSent + DepositForBurn, matching immutable burn body, standard received finality and MintAndWithdraw to the configured USDC vault. Require exact net payout after an explicit maximum/actual fee, with expiration valid at mint time. Restrict the first adapter to one source and destination transfer per transaction. Unsupported versions, hooks, Fast Transfers, ambiguous batches and missing/malformed data hold; authenticated binding mismatches reject.
**Identity and beneficiary:** Release ID is domain-separated ABI hashing of source chain, transmitter, transaction hash and log index. A 64-byte Tripwire metadata hook binds the end beneficiary; it is not an executable Circle hook. Mint recipient is the vault. Stable source identity plus Circle nonce and settlement uniqueness prevent multiple release credits from one transfer.
**Persistence and guards:** Schema v3 binds the adapter fingerprint and persists immutable exact proof fields, payload hashes, provenance and unique source/settlement/nonce claims before VERIFIED. Guard every tick/sign/publication with prior accepted proof anchors. Finalized conflicts persist a source quarantine even during a standalone audit before watcher state exists; restart cannot clear it. Lagging RPC is unavailability. V1/v2 are refused with existing queue/outbox retained; no live migration performed.
**Runtime boundary:** Pure codecs and officially sourced ABIs/addresses live in `src/chains/evm/`; adapter I/O, SQLite, audit and signing integration stay in operator scripts. Use existing viem RPC clients/retries/timeouts, with abortable transports for the audit, rather than adding an Iris HTTP service/dependency. `createCctpRpcOperator` opts into the adapter; legacy demo commands remain unconfigured. The read-only audit reads finalized vault bindings/releases, requires no private key and never submits transactions.
**Trust/limits:** Circle contracts/attesters and honest RPC answers remain trusted. Base's finalized head is L1-derived; this adapter does not independently derive L1 consensus. It gates funds already minted into an isolated vault; it cannot pause permissionless CCTP. The vault's oracle still has authority to approve arbitrary owner-created requests, so a compromised oracle is not contained by an on-chain source verifier. Production needs an authenticated on-chain request/escrow boundary, external review and a live observe-only pilot. Existing USD behavioral heuristics remain illustrative, with a $1 assumption for testnet USDC; live pricing/baselines are future work.
**Validation:** 45 synthetic protocol/adversarial vectors cover identities, exact fees/large amounts, pending finality, malformed receipts, atomic claims/restart, independent nonce replay and standalone/watcher quarantine; finalized feed provenance-aware filtering and v1/v2 queue preservation are also covered. No live CCTP transfer is claimed. [Runbook and official fact sources](plans/tripwire-cctp.md).

### ADR-018 — Atomic authenticated CCTP escrow credits
**Status:** Authorized by the human's instruction to check new changes and continue Tripwire hardening, 2026-10-01. Extends ADR-017; no public deployment or journal migration performed.
**Context:** The generic demo vault lets its owner create arbitrary requests. An independent offchain source verifier cannot stop a compromised review oracle from approving one of those requests. CCTP's attested destination message has no source transaction/log identity, so its on-chain credit cannot use ADR-017's source-derived ID.
**Decision:** Add a separate `CctpEscrow` inheriting the existing review/guardian gate with `owner = address(this)`. No external actor can create requests, transfer ownership or withdraw. A permissionless `receiveCctp` validates exactly the known v2 header/body and 64-byte beneficiary hook, configured domains/messengers/source token, canonical EVM address words, standard minimum/executed finality 2000, bounded fee and valid expiration. Require `destinationCaller = escrow` to prevent a direct Circle relay consuming the nonce and minting without a credit. Call the configured Circle transmitter for attestation verification/mint, require an exact net balance increase, then self-call `requestRelease` with authenticated recipient/net amount. Record nonce/payload hash and emit credit evidence. Any failure rolls back the local credit and Circle's mint/nonce. Existing pooled balance cannot substitute for a mint. Zero/self beneficiaries and reentrant receives are refused.
**Identity:** `keccak256(abi.encode(keccak256("Tripwire/CCTP/v2/escrow/v1"), block.chainid, address(this), sourceDomain, nonce))`. The nonce is Circle's attested nonzero destination nonce, not the zero value emitted on the source. The operator still authenticates finalized source MessageSent/DepositForBurn and enforces source-event, settlement and nonce uniqueness independently.
**Operator policy:** Authenticated verification requires mint, MessageReceived, ReleaseRequested and CctpEscrowFunded in one finalized destination receipt, in that order, matching immutable fields, exact net amount, nonce-derived ID and reconstructed attested payload hash. Request provenance is checked even when backing was cached. The signing factory checks version/self-owner and configured Circle bindings at finalized state before opening its lifecycle. Configuration getters are not proof of bytecode authenticity; the reviewed deployment/manifest remains trusted. Read-only manifest v2 selects this policy; v1 preserves explicit legacy audits and labels their output. Pure IDs/layout/ABI stay in the EVM layer; RPC, SQLite and signing stay outside the browser.
**Compatibility:** Schema remains v3, with a different policy fingerprint. The adapter defaults to authenticated escrow; legacy use requires an explicit policy argument. Legacy journals, IDs and vaults cannot be reused silently. A fresh escrow deployment and explicit reconciliation of outstanding funds/queues/signed work are needed; no automatic upgrade, reset or migration. Source discovery hints keep source-derived IDs; locators bridge attested request IDs to actual source positions.
**Trust/limits:** Circle contracts, attesters and USDC are trusted; finalized evidence still relies on honest RPCs. A Tripwire oracle can approve/hold/reject authentic funded credits, but cannot invent them or alter their payout fields. It can deny service or allow a risky genuine beneficiary. Guardian owner/configuration remains trusted. Rejected credits remain locked; refunds/recovery need an explicit future policy, not an administrator withdrawal bypass. This contains credit forgery for this escrow, not all bridge/oracle risks or permissionless CCTP globally. External review and a recorded testnet/observe-only pilot remain pending.
**Validation:** 42 EVM regressions, 19 authenticated source/settlement/restart vectors, 12 deployment/manifest/ABI checks and fresh compile/size consistency. Eight new guard mutants join the 21 existing guardian/review cases. The local one-attester harness is explicitly synthetic and excluded from deployable escrow artifacts; Circle's full threshold implementation is not claimed to run locally. [Runbook and pinned official sources](plans/tripwire-cctp.md).

### ADR-019 — Refresh freshly justified pending protection before expiry
**Status:** Authorized by the human's instruction to continue Tripwire's hardening plan, 2026-10-01. No live refresh/deployment performed.
**Context:** The guardian already accepts same-tier refreshes, preserving DELAY's original hold window, but `Attestor` skipped `tier <= active`. A persistent held request could silently lose its route protection after 24 hours. A local last-send timestamp would be wrong after restart, external attestations, owner actions or a receipt reorg.
**Decision:** Keep continuous refresh inside the existing operator tick. Re-evaluate pending requests each tick; escalate higher current risk immediately and refresh a matching active tier when at most one hour remains. Lower fresh risk never extends a higher tier. Read tier, expiry and oracle at one latest block, validate the boundary and recheck number/hash/timestamp; refuse a head behind any observed journaled write receipt. Use that block's clock for expiry and signature TTL. Serialize attestor calls. Legacy fixture/demo ports may escalate without this snapshot but cannot infer refresh; a failed configured snapshot cannot fall back to a legacy tier read.
**Failure behavior:** Missing/clear/invalid assessments never reuse an old high score. Malformed/unavailable guardian state, unconfigured routes and oracle rotation return unavailable before signing; the release runner retains the request and skips review/payout. Source canonical checks still run before signatures/publication, and quarantine stops refresh. Pending protection uses the existing durable transaction journal and nonce/recovery rules. Reads of latest guardian state do not weaken finalized source proof or terminal acknowledgement policy. Host/provider clocks and exact snapshot validity are separate from signature authenticity; the contract still enforces its signer/TTL and tier rules.
**Persistence:** No schema change or new incident table. Restart re-reads actual chain expiry; signed refresh work replays original outbox bytes. Completed/rejected jobs are not forever-open incident flags. Successful refresh state suppresses duplicates across restart, while an unresolved signed transaction blocks another nonce. Source guards and receipt reconciliation run before new refresh work. Owner resume may be followed by a new escalation from freshly reassessed pending risk; stop/reconcile the operator when human review intends to suppress that response.
**Limits:** A process/RPC/data outage can let protection expire. After an offline gap, fresh risk can establish a new tier; entering DELAY again opens a new review window. Protection is not renewed from stale cached assessments or from a historical terminal request merely to keep a route blocked. Independent pending/held release reviews remain fail-closed. Real baselines, reliable data/sender operation, incident policy and observe-only pilot remain separate work. Default refresh buffer 3600 seconds (configurable 1–3600), signature TTL 300 (1–600); these are operator policy, not changes to the guardian's 24-hour expiry.
**Validation:** 24 direct EVM/state-boundary expiry, restart, clock, concurrency, rotation and failure cases plus four durable-queue regressions for fresh re-evaluation, restart, unavailable reconciliation and quarantine. Existing guardian/vault bytecode and browser paths are unchanged. [Operator runbook](plans/tripwire-operator.md).

### ADR-020 — Isolate route reporters, retain rolling spend and delay each large request
**Status:** Authorized by continued Tripwire hardening work, 2026-10-01. Implemented locally; external review/fresh deployment pending.
**Context:** Four regressions demonstrated that a globally allowed reporter could exhaust another route, a fixed-window boundary admitted two caps seconds apart, cap reconfiguration erased spend, and a newly reviewed large request bypassed DELAY after its route-wide window. Request retry also needed a defined review/expiry policy.
**Decision:** Replace global grants with caller/route pairs. Enforce a conservative rolling budget in 17 fixed buckets, width ceil(window/16), expiring an entire bucket one window after its last spend. This upper-bounds every true rolling window with bounded work/storage; one-hour conservatism is at most 224 extra seconds. Cap updates/resume/tier changes preserve spend; window length is immutable. Views age usage out. For large requests under DELAY, first ALLOW establishes a sticky 30-minute per-message clock; re-review/HOLD/resume cannot shorten or restart it, and another request cannot reuse it. Current tier controls the policy even when minimumTier is NONE. Existing ALLOW/signer/TTL/nonce/tier/guardian/token gates remain mandatory.
**Operator:** Read request/delay/clock from one hash-checked latest block, bounded below by observed write receipts. Reassess pending risk and source health each tick; while an existing verified ALLOW decision awaits its request clock, avoid repeated review signatures. HOLD/REJECT still revoke immediately. At maturity use a fresh review and execution simulation. Source finality/quarantine, durable raw-byte recovery and finalized terminal acknowledgement remain unchanged.
**Compatibility:** Immutable guardian/release policy markers and release-review domain version are 2. Signing startup checks both markers and the scoped vault grant. Existing deployments cannot be upgraded in place; explicit funded-credit/queue/outbox reconciliation precedes a fresh deployment. Scope-bound SQLite schema stays unchanged, with no automatic migration/reset/credit transfer. Historical read-only CCTP source audits remain possible and do not certify current release policy. Getters validate trusted deployment configuration, not arbitrary bytecode authenticity. Browser replay uses new local bytecode and explicit grants; no public-network signing enters browser/proxies.
**Tradeoffs/validation:** Conservative buckets can delay honest volume slightly beyond the nominal window; warmed hook gas rises from about 37k to 79k. Authorized route reporters/owner/oracle and honest RPCs remain trusted within their existing roles. Four regressions failed before implementation; 42 new tests (including CCTP, independent rolling ledgers and durable/RPC failures) bring the suite to 609. Nine new contract mutation guards and regenerated artifact consistency accompany the change. [Detailed policy and rollout](plans/tripwire-route-policy.md).

### ADR-021 — Threshold attestation: a self-governing k-of-n quorum as the oracle
**Status:** Implemented locally 2026-10-01 at the human's request to bring Tripwire to its settlement-firewall brief ("move from one signer toward threshold / multi-party attestations"). No public deployment.
**Context:** One oracle key signed every route attestation and every release review. A stolen key could approve any pending request the bridge failed to authenticate, and ADR-012 named the single signer as the centralisation point.
**Decision:** Add `TripwireQuorum`, an ERC-1271 contract holding up to 16 attestors and a threshold with an honest-majority rule (`2 * threshold > n`; 1-of-1 allowed for local development). A valid signature is at least `threshold` 65-byte ECDSA signatures over the caller's own EIP-712 digest, in strictly ascending signer order, so a repeated key counts once and outsiders never count. Membership changes only through `updateSigners`, signed by the current quorum over an EIP-712 `UpdateSigners(address[] signers,uint256 threshold,uint256 epoch)` bound to the contract and chain; each change bumps `epoch`, so approvals cannot be replayed. There is no owner. The guardian and vault keep their single-key behavior unchanged: an EOA oracle is still recovered and compared; a contract oracle is asked through OpenZeppelin `SignatureChecker`'s ERC-1271 call. No other guardian or vault rule changes; a quorum can do exactly what one oracle key could.
**Operator:** `scripts/tripwire/quorum.ts` presents the set as a viem account whose address is the quorum contract, so `Attestor` and `signReleaseReview` work unchanged. Each `QuorumMember` receives the full typed request and may refuse; the aggregator recovers every returned signature, discards ones that do not match their member, orders and truncates to exactly `threshold`, and fails with `QuorumUnavailableError` below it.
**Compatibility:** `GUARDIAN_POLICY_VERSION` and `RELEASE_POLICY_VERSION` are 3; `assertProtectionPolicy` refuses v2. The vault's EIP-712 domain stays version 2: the review payload is unchanged. Existing deployments cannot be upgraded in place; fresh deployment and explicit reconciliation as in ADR-020.
**Trust/limits:** Rotating membership inside the same quorum leaves an already-accepted ALLOW valid until its review expiry (at most 10 minutes); installing a new quorum takes the owner two days' notice (`proposeOracle` → `acceptOracle`, ADR-024) and invalidates outstanding reviews when it lands, while `disableOracle` stops every key at once. If a majority of keys is lost, the guardian owner proposes a new quorum. The guardian owner remains trusted. Members must run independent verification on separate infrastructure for the threshold to mean anything; the local tests co-locate keys and say so. A quorum tightening a route also needs `threshold` signatures — a minority cannot freeze alone, which trades some response speed for denial-of-service resistance.
**Validation:** 25 EVM tests (threshold, repeat, order, outsider, digest binding, malformed lengths, escalate-only, constructor rules, rotation, replay, vault ALLOW/rotation, independent refusal). Ten mutants (seven quorum, two guardian, one vault) join the mutation run. Runtime: guardian 7,821 bytes, CCTP escrow 10,214 bytes. [Build map](plans/tripwire-settlement-firewall.md).

### ADR-022 — Independent verification across RPC providers
**Status:** Implemented locally 2026-10-01 under the same instruction as ADR-021. No live operation.
**Context:** Finalized observations (ADR-016) and the CCTP adapter (ADR-017/018) read every receipt and header through one endpoint. ADR-018 records the residual risk: "finalized evidence still relies on honest RPCs". A single lying provider can fabricate a burn and a mint that verify; a regression test now demonstrates exactly that.
**Decision:** `rpcQuorum(providers, { quorum })` implements the adapter's existing `CctpRpc` interface over independently operated providers. At least `quorum` providers must answer (minimum 2 when 2 or more are configured), and every provider that answers must agree on the canonical content: chain id; header number, hash, parent and timestamp; receipt status, block and every log field a proof reads. Presentation-only receipt fields are ignored. One dissent is `RpcDisagreementError` and the release is UNAVAILABLE (held, retried) — never approved. The finalized head is the highest block that at least `quorum` providers report finalized, re-read by number only from those providers; disagreement among them is a `FinalityConflictError` and quarantines the operator. A lagging provider can delay, never approve and never quarantine.
**Wiring:** `createCctpRpcOperator` accepts `verifiers: { source, destination, quorum }`; `tripwire:cctp:verify` reads `BASE_SEPOLIA_VERIFIER_RPC_URLS`, `SEPOLIA_VERIFIER_RPC_URLS` and `TRIPWIRE_RPC_QUORUM`. Default quorum is every configured provider. Without verifiers the previous single-provider behavior is unchanged.
**Limits:** Agreement among providers is not a consensus proof; providers sharing an upstream are not independent. Event discovery (`eth_getLogs`) still uses the primary client; it is a hint, and every proof is re-read through the quorum. A light-client finality check remains roadmap.
**Validation:** 13 tests, including the end-to-end case where the same fabricated CCTP receipts verify through one provider and are held through two.

### ADR-023 — One proof-first settlement verdict, and tighten-only route policy
**Status:** Implemented locally 2026-10-01 under the same instruction as ADR-021.
**Context:** The rule "proof first; heuristics only support" was spread across the watcher, `review.releaseDecision` and the scorer, and the operator recorded only ALLOW/HOLD/REJECT. The operator's decision and the review port's signed decision are computed in two places, so any per-route input must reach both identically.
**Decision:** `scripts/tripwire/settlement.ts` exposes `settlementVerdict(observation)`: a decision, the route tier the evidence justifies, the deciding reason and seven named checks of two kinds. PROOF: `source_authenticated_final`, `backing_covers_release` — a failure is REJECT and recommends FREEZE; unknown holds. SAFETY: `risk_assessed`, `oracle_health`, `counterparty_screen`, `route_policy_size`, `risk_below_hold` — failure or unknown only HOLDs; safety can never approve a failed or unknown proof and never rejects on suspicion. The function is pure. `releaseDecision` delegates to it. `RoutePolicy` (`maxSingleRelease` in base units; `holdAtScore` within 0.65–0.95) can only add holds; it is validated when the watcher is built and attached to every observation, so every decision and every signed review read the same policy. Operator results carry the deciding `reason`.
**Compatibility:** An 800-case grid proves the verdict equals the replaced rule for every assessment the scorer can produce. It is deliberately stricter on one incoherent input the scorer cannot emit (a screening hit with a sub-hold score): that now holds. No contract, schema or signing-format change.
**Validation:** 14 tests: the equivalence grid, proof-first REJECT/HOLD, suspicion holds but never rejects, the check record, determinism, policy holds and schema refusals, watcher attachment.

### ADR-024 — Bounded owner and oracle powers: time-locked rotation, kill switch, protection span, cumulative DELAY
**Status:** Implemented locally 2026-10-02 at the human's request to remediate the Tripwire audit of `0134301` (CRIT-1, HIGH-3, MED-1). No public deployment.
**Context:** The audit drained a FROZEN 5,000,000-unit route in consecutive transactions: the owner called `setOracle(self)` (instant), `resume`, raised the cap, requested a release and signed its own ALLOW. On Sepolia one hot key was owner, oracle and relayer. Separately, an oracle could refresh FREEZE forever (the PoC held a route 161 hours), and DELAY limited each payout to a tenth of the cap but not their sum (4 × 10% passed).
**Decision:** `setOracle` is gone. `disableOracle()` sets the oracle to zero at once: every attestation and review fails. A replacement is `proposeOracle(next)`, then `acceptOracle()` (callable by anyone) no sooner than `ORACLE_ROTATION_DELAY` = 2 days later; `cancelOracleRotation()` withdraws it. `configureRoute` refuses to raise a cap while any tier is active (`RaiseDuringProtection`). The oracle alone holds a route for at most `MAX_ORACLE_PROTECTION` = 72 hours from the span's start: refreshes clamp expiry to the span's end, and an attestation that could not reach past now reverts `ProtectionSpanExhausted`. A new span opens only with no tier active and 72 h + `PROTECTION_COOLDOWN` (24 h) after the last span began; the owner's `rearmProtection(routeId)` starts one at once for a real incident, and `resume` clears the span. `protectionLimit(routeId)` reports the expiry an attestation could set now. Under DELAY the route counts everything paid since DELAY began (`delayedOutflow`, reset on entering DELAY and on resume); the total may not pass a tenth of the cap, and `outflowDelay` reports the same.
**Trust:** The owner is still trusted for availability (resume, re-arm, kill switch) but can no longer become the oracle faster than two days, in public (`OracleRotationProposed`). Owner alone cannot pay out: every payout needs an oracle-signed ALLOW. Owner and oracle on one key can, which is why ADR-026 forbids it. `disableOracle` is a denial-of-service lever by design: frozen, never stolen.
**Operator:** The attestor reads `protectionLimit` at the same hash-checked block as tier and expiry, and signs nothing once the span is spent or a refresh could not extend it.
**Compatibility:** `GUARDIAN_POLICY_VERSION` is 4 and `assertProtectionPolicy` refuses 3 ("instant-rotation guardian"). The EIP-712 domain is unchanged. Fresh deployment and reconciliation as in ADR-020.
**Validation:** `contracts/evm/test/auditRegression.evm.test.ts` inverts the audit's contract PoCs (14 tests), plus rotation, kill-switch, span and split-payout tests; 62/62 contract mutants caught, 14 of them new. Runtime: guardian 9,510 bytes; accepting an attestation costs 88.3k gas (84.5k before: the span start is one more storage write), a warm outflow check 79.0k as before.

**Addendum, 2026-10-04 (integration review):** `disableOracle` now also cancels a pending rotation. Before, a rotation proposed earlier survived the kill switch and anyone could accept it once its notice ended, quietly re-enabling a key the owner had just switched off. Re-enabling now always takes a fresh `proposeOracle` and the full two days. `GUARDIAN_POLICY_VERSION` stays 4: nothing the operator relies on changed. The Sepolia guardian deployed on 2026-10-03 predates this; its owner Safe must batch `cancelOracleRotation` with `disableOracle` if a rotation is ever pending. Guarded by a new test and mutant ("kill switch: a pending rotation survives it").

### ADR-025 — A REJECT is a seven-day hold, not an end
**Status:** Implemented locally 2026-10-02 under the same instruction as ADR-024 (CRIT-2).
**Context:** REJECTED was terminal and `CctpEscrow` has no rescue path, by design. One wrong REJECT (an adapter bug, a misconfiguration, a compromised oracle) stranded fully backed, Circle-minted USDC for good; the PoC showed a later ALLOW failing and the beneficiary at zero.
**Decision:** `RELEASE_POLICY_VERSION` is 4. A REJECT records `rejectedAt[messageId]`; no review is accepted for `REJECTION_COOLDOWN` = 7 days, after which a fresh review with a higher nonce may ALLOW, HOLD or REJECT again (a new REJECT restarts the hold). A reopened release still pays only its recorded recipient, which in `CctpEscrow` is the authenticated hook beneficiary: nothing can be redirected. The review payload and EIP-712 domain version 2 are unchanged.
**Operator:** REJECTED is never acknowledged. The operator reads `rejectedAt` with the request at one hash-checked block, sleeps through the hold, and afterwards reopens a request only when `settlementVerdict` is ALLOW on fresh evidence; otherwise it stays rejected and nothing is signed.
**Tradeoffs:** A compromised oracle could ALLOW a rejected request after 7 days, as it could any pending one; the hold gives humans a week to `disableOracle`. Rejected requests stay in the queue; backoff (ADR-027) keeps their cost small.

### ADR-026 — Separate keys, separate nonce lanes, fee-bumped replacement
**Status:** Implemented locally 2026-10-02 under the same instruction as ADR-024 (HIGH-1; the brief's three key roles). The Sepolia redeploy needs the role keys and a Safe and has not been run.
**Context:** Every transaction shared one signer and one nonce: an underpriced review blocked the FREEZE attestation behind it, and recovery rebroadcast identical bytes forever, during exactly the gas spike an exploit brings. On Sepolia the same key was also owner and oracle (CRIT-1).
**Decision — roles:** An owner Safe (a contract; the deploy refuses an EOA and offers ownership through Ownable2Step), an oracle key that signs attestations and reviews and pays no gas, a release relayer that deploys and pays for reviews and payouts (it also owns the demo token and vault, standing in for the bridge), and an attestation relayer. `.env.tripwire` names them `TRIPWIRE_ORACLE_KEY`, `TRIPWIRE_RELAYER_KEY`, `TRIPWIRE_ATTESTATION_RELAYER_KEY` and `TRIPWIRE_OWNER_SAFE`; all must differ. The deploy and the durable operator refuse a single key; a legacy one-key file still loads for verification.
**Decision — lanes:** Attestations are authenticated by their signature, not their sender, so they get their own relayer, journal (`<state>.attestations.sqlite`) and `DurableSender`. Each lane still allows one outstanding nonce. If the release lane cannot recover, reviews and payouts wait with the reason while attestations run; a failed attestation becomes a retry for that release, not a failed tick. Finality conflicts still stop everything.
**Decision — fees:** New transactions offer twice the base fee plus the tip and a fifth more gas than estimated, capped by `TRIPWIRE_MAX_FEE_GWEI` (default 300); nothing is signed when the network costs more. When a transaction is not mined in time or a node calls it underpriced, the sender journals a re-signing with the same nonce, gas and call and both fee caps at least 10% higher (the port offers the larger of +12.5% and the current price), then broadcasts it. Replacements are append-only, journaled before broadcast, accepted only while nothing is mined, and capped at 8; a receipt for any version settles the transaction (`minedHash`), and two versions reporting receipts halts. "Insufficient funds" surfaces at once instead of timing out.
**Limits:** A bump keeps the content: an attestation or review that expired while stuck reverts when mined, wasting its gas but freeing the nonce; the operator then signs afresh. The operator signs with one oracle key: `TripwireQuorum` (ADR-021) is enforced on-chain, but its members are not yet run independently (MED-5).
**Validation:** `scripts/tripwire/__tests__/auditRegression.test.ts` inverts the audit's sender PoC: the FREEZE is sent from its own lane while a review is stuck at 1 wei, and recovery bumps the review 1 → 32 wei until it mines. Sender, fee-policy, role and deploy tests cover the rest.

### ADR-027 — The live operator's data path: rolling baseline, safe-head requests, exact backing, failover
**Status:** Implemented locally 2026-10-02 under the same instruction as ADR-024 (HIGH-2, MED-2, MED-3, MED-4).
**Baseline (HIGH-2):** Nothing computed one, so the live operator held every honest payout. `computeBaseline` summarises the route's finalized source burns over a 1–168 hour window (default 24): count, median and p95 in base units by nearest rank, the vault's token balance as the pool, stamped with the tick clock. Burns rather than executed payouts, because payouts need a baseline first: built from payouts, a new route could never start. Below the scorer's 20 samples, or if the balance read fails, there is no baseline and payouts hold. Known limit: someone bridging honest volume first can shape the baseline; size, velocity, pool share, proof and screening signals still apply.
**Latency (MED-2):** Release requests are read at the `safe` head through the same hash-linked anchors (a reorg past it quarantines); source events stay `finalized`, and the store refuses anything else for them. Recipient lookups run four at a time and cache successful answers for 10 minutes; source verification stays sequential because it claims proofs. Held and rejected releases are re-checked on a doubling interval (30 s to 10 min) in the RPC operator, and a REJECT sleeps through its hold.
**Availability (MED-3):** Comma-separated RPC URLs fail over in order: one 10-second try per endpoint per round, two rounds. viem's ranking is not used: its timer never stops, so a finished CLI would not exit. Every read that matters stays hash-checked, so endpoints cannot be mixed silently. Consecutive failed ticks back off from 10 seconds to 5 minutes.
**Backing (MED-4):** The exact backing check is one-sided: a payout may come in under its burn by the route's tolerance, never over it, and the default tolerance is 0. The USD comparison used only by historical replays is unchanged.
